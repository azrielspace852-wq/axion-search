AXIONSearch

Architecture Blueprint

AXION Search v4.2 uses Cloudflare Pages for the static site and Cloudflare Workers for the API. Pages Functions connect to the API Worker using a Service binding.

Architecture and request flow

Browser / SDK client
   │
   ├── Website: https://search.xxn.cc.cd
   │      ├── Static HTML / CSS / JS / SDK
   │      ├── localStorage: theme/language/preferences
   │      └── IndexedDB: search history
   │      └── Pages Functions: /api/* and /health
   │                    │
   │                    └── Service binding: AXION_SEARCH_API
   │                                  │
   └── External API client ───────────┤
                                      ▼
                         Worker: axion-search-api
                         https://api.search.axn.cc.cd
                           ├── Search provider orchestration
                           ├── SafeSearch + dedupe
                           ├── Legacy-compatible API routes
                           └── Grounded AI summary + chat

Deployment configuration

  • pages/wrangler.jsonc configures the Pages project and the AXION_SEARCH_API Service binding.
  • workers/wrangler.jsonc configures the API Worker and its custom domain.
  • pages/functions/api/[[path]].js forwards website API requests using the binding rather than a public Internet fetch.
  • Production uses only Cloudflare Pages + Workers; the release does not include a legacy Node server, Cloudflare Tunnel, or VPN/proxy runtime.

Provider orchestration invariants

  1. Rotation: the provider ordering rotates by minute to distribute load.
  2. Resilience: each configured provider is attempted; one blocked or empty provider does not stop other providers from returning results.
  3. Merge: results merge in rotation order and are de-duplicated by link.
  4. SafeSearch: negative terms are added to queries and a second filtering pass blocks known NSFW terms in returned results.
  5. AXION priority: AXION-related web queries prepend results for site:axn.cc.cd; the dedicated axion type stays ecosystem-focused.
  6. Provider privacy: provider identities and API secrets are not returned to the browser.

AI invariants

  1. Summaries use the query and a limited set of retrieved search results as grounding context.
  2. The prompt instructs the model to state when evidence is insufficient and to cite sources by result number.
  3. The model is not client-selectable. The Worker automatically rotates between gemma-4-31b-it and gemma-4-26b-a4b-it; temperature and output tokens remain bounded.
  4. Up to three Google AI Studio keys are rotated on failures/quota errors. Responses stream live through SSE.
  5. Without an AI secret, search still works; summary/chat report AI as not configured.

Runtime and security boundaries

  1. The Worker uses the Fetch API and request-scoped environment bindings; Express does not run in production.
  2. AI keys and optional Brave credentials are stored as Cloudflare Worker secrets, never in frontend files.
  3. Pages invokes the API Worker using an internal Service binding. Third-party SDK consumers use the API domain and CORS.
  4. The active Worker uses native fetch() without VPN or proxy configuration. The deployment has no Tunnel dependency.

Browser data invariants

  1. Theme/language/preferences remain in localStorage; search history is stored in IndexedDB and migrated from the legacy localStorage key when possible.
  2. Preference export/import remains a JSON-based device migration path.
  3. SafeSearch remains enabled by default unless the user changes the setting.
